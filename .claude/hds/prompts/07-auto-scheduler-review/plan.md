The existing stack, with no new runtime dependency. The pure scheduling package `hds.scheduling` (standard library, with OR-Tools only in `cpsat.py`) gains: locks as fixed assignments (H6); a starting roster with a change penalty, passed to CP-SAT as solution hints; the two run controls mapped onto the organisation's weights; preference chips as soft terms weighed second, after coverage; and, for each unfilled slot place, a step-by-step explanation built from the rule checks in `eligibility.py` and `rules.py`, not from CP-SAT's infeasibility core. "Who else could cover" is a pure function over the same checks, across every project. Interim results: a CP-SAT solution callback hands the worker the best result so far, which the worker stores on the job at most every two seconds; "stop and use best so far" is a flag on the job that the worker checks. Proposal edits, partial accepts, chips and the run record are append-only rows, and locks are a column on assignments, all through Alembic migrations. API changes go contract-first in the 001 OpenAPI, then the client is regenerated; Manager scope follows 007's run rules. The client builds on 007's run page, roster, toasts and design system; the in-app notice comes from the job's status, with no push. Tests: Hypothesis properties that no proposal breaks a hard rule under any locks, controls and chips, and that every lock is kept; example tests for each reason code; contract tests; Playwright specs under apps/client/tests/e2e/ux/ in Hebrew and English, at desktop and phone sizes, with axe-core. One session builds both the backend and the client, so tasks carry no [UI] or [CORE] mark. Group the tasks into four pull requests: (1) review as a change, partial accept and editing; (2) empty-slot reasons and fixes; (3) steering, trade-offs and fairness; (4) best so far and stop, the run record, and the one continuous flow.
